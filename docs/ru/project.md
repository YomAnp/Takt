# Устройство Takt

[На главную](index.md) · [English](../en/project.md)

Этот документ описывает выбранный стек и разделение ответственности в Takt. Его основа — личный учёт времени по отметкам сотрудника. Общение и внешние интеграции не входят в описанный здесь контур.

## Учёт времени

Норма, отметки и расчётный результат — разные данные. Норма определяет требуемую длительность; отметки описывают события; расчёт применяет правила к этим событиям. Расписание занятий и учебная нагрузка не заменяют норму присутствия.

| Термин | Значение |
| --- | --- |
| Требуемое время | Длительность присутствия, которую нужно набрать за установленный период |
| Интервал присутствия | Промежуток между приходом и уходом; у незакрытого интервала ещё нет отметки ухода |
| Исключаемый перерыв | Время внутри интервала присутствия, которое не засчитывается по применимым правилам |
| Учтённое время | Длительность, засчитанная по отметкам и правилам |
| Остаток | Время, которого не хватает до нормы; после её выполнения остаток равен нулю |
| Расчётное время выполнения нормы | Прогноз момента выполнения нормы при явно указанных условиях дальнейшего присутствия |

### Пример расчёта

Сотрудник пришёл в 08:30. Требуемое время — 6 обычных часов по 60 минут. К 13:10 уже состоялся исключаемый перерыв длительностью 30 минут. Все отметки относятся к одному дню в одном часовом поясе; других ограничений и последующих перерывов в примере нет.

| Расчёт | Результат |
| --- | --- |
| Время с прихода: 13:10 − 08:30 | 4 ч 40 мин |
| Учтённое время: 4 ч 40 мин − 30 мин | 4 ч 10 мин |
| Остаток: 6 ч − 4 ч 10 мин | 1 ч 50 мин |
| Выполнение нормы при непрерывном присутствии: 13:10 + 1 ч 50 мин | 15:00 |

Это пример арифметики, а не расписание колледжа. Новый исключаемый перерыв или исправление отметки изменят прогноз.

### Требования к расчёту

Пересекающиеся интервалы не должны давать двойной учёт, а повтор одного запроса — создавать повторную отметку. Одновременные исправления должны сохранять согласованность записей. Для незакрытого дня результат должен указывать момент, на который выполнен расчёт; истечение нормы само по себе не означает уход сотрудника.

Время события отличается от времени внесения записи: приход в 08:30 можно записать позднее. Часовой пояс и граница дня должны быть явными, в том числе для интервала через полночь. Пересчёт после изменения нормы должен объяснять, какие записи и правила использованы.

Происхождение нормы, право её менять, период учёта и перенос часов определяют область действия правил. Засчитываемые перерывы, работа вне колледжа и несколько интервалов за день определяют состав учтённого времени. Обычные и академические часы нельзя смешивать без согласованного преобразования. Эти правила, округление и трактовка превышения нормы требуют согласования. Порядок исправлений, их согласование и история изменений также не определены.

## Компоненты и зависимости

Один репозиторий объединяет клиент, сервер и документацию. Сервер организуется как одно приложение с внутренними модулями: известный сценарий не требует независимых сервисов, а совместное изменение расчётов и API удобнее проверять в одном pull request.

| Компонент | Ответственность |
| --- | --- |
| Telegram Mini App | Показывать состояние, принимать действия сотрудника и обращаться к API |
| Python-сервер | Проверять доступ, сохранять отметки и правила, выполнять расчёты и возвращать объяснимый результат |
| PostgreSQL | Хранить исходные записи, данные пользователей и применимые правила |
| Интеграция с Telegram | Проверять входные данные Telegram и связывать подтверждённую идентичность с проверкой доступа |

Расчёт принадлежит серверу, чтобы повторное открытие Mini App восстанавливало состояние по сохранённым данным. Локальный таймер отображает прогноз; закрытие приложения не останавливает учёт. Обновление цифр на экране не требует отправки серверного сообщения каждую секунду. Статистика читается из данных учёта и использует те же правила.

Внутри сервера ответственность разделяется по предметным областям:

| Область | Содержание и допустимые зависимости |
| --- | --- |
| Идентификация и доступ | Идентичность сотрудника и разрешения на операции; принимает проверенные данные Telegram, не выполняет расчёты времени |
| Правила времени | Нормы и условия зачёта; не зависит от HTTP и Telegram |
| Учёт | Отметки, интервалы и расчёты; использует правила времени, а сценарии записи обращаются к проверке доступа и хранилищу |
| Telegram | Адаптер официального API; передаёт проверенную идентичность области доступа, не содержит своей копии правил учёта |

HTTP-обработчики проверяют форму запроса и вызывают сценарий приложения. Сценарий координирует доступ, чтение, расчёт и запись. Арифметика времени остаётся обычными функциями, проверяемыми без HTTP-сервера, Telegram и базы данных. Код размещается по ответственности; общие `utils`, `core` или каталоги моделей не должны скрывать предметные границы.

### Доступ через Telegram

Сервер должен проверять подлинность `initData` по официальному алгоритму и актуальность `auth_date`. Значения из `initDataUnsafe` не являются доверенным источником авторизации. См. [проверку данных Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Подтверждённый Telegram-пользователь не обязательно является сотрудником колледжа и не получает из этого факта доступ к чужим записям. Способ подтверждения принадлежности к колледжу, модель сессии и видимость индивидуальных данных требуют отдельного решения. Поддержка одного или нескольких колледжей влияет на границы доступа к данным.

## Выбранный стек

| Область | Инструменты | Назначение |
| --- | --- | --- |
| Сервер | Python, FastAPI | HTTP-обработчики, зависимости и вызов сценариев приложения |
| Контракт | Pydantic 2, OpenAPI | Проверка формы данных, схемы запросов и ответов, описание API |
| Настройки | pydantic-settings | Типизированные настройки из окружения |
| Хранение | PostgreSQL | Постоянные данные учёта и пользователей |
| Доступ к БД | SQLAlchemy 2.0, Psycopg 3 | Запросы, модели хранения и транзакции |
| Миграции | Alembic | Изменения схемы БД |
| Клиент | React, TypeScript, Vite | Интерфейс и сборка приложения для Telegram WebView |
| Клиент API | Hey API: `@hey-api/openapi-ts` | Генерация TypeScript-клиента и типов из OpenAPI |
| Серверные данные в интерфейсе | TanStack Query | Загрузка, кэширование и обновление данных |
| Стили | CSS | Оформление интерфейса |
| Python-окружение | uv | Управление зависимостями и их фиксация |
| Проверки сервера | pytest, HTTPX, Ruff, mypy | Тестирование поведения и HTTP API, форматирование, статический анализ и проверка типов |

FastAPI обрабатывает запросы, REST задаёт подход к организации HTTP API, OpenAPI описывает контракт. Эти инструменты выполняют разные задачи. Связь операций и схем с OpenAPI описана в [документации FastAPI](https://fastapi.tiangolo.com/features/).

Для работы с БД выбран `AsyncSession` SQLAlchemy с асинхронным Psycopg 3. Границу транзакции определяет сценарий приложения; одна сессия не разделяется между параллельными задачами. Асинхронность здесь относится к вводу-выводу и не является обещанием ускорения расчётов. См. [диалект Psycopg](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#module-sqlalchemy.dialects.postgresql.psycopg) и [правила работы с AsyncSession](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks).

Клиент обращается к официальному Telegram WebApp API. Для обработки команд бота выбран aiogram 3, если такая задача входит в согласованный объём. Библиотека бота не заменяет проверку `initData`; доставка отложенных уведомлений требует отдельного механизма хранения заданий и повторных попыток. См. [Telegram Mini Apps](https://core.telegram.org/bots/webapps) и [aiogram](https://docs.aiogram.dev/en/latest/).

Точные версии Python, Node.js, PostgreSQL и библиотек фиксируются вместе после проверки совместимости. Зависимости и их обновления должны быть воспроизводимыми.

### Контракт API

Источник контракта — операции FastAPI и схемы Pydantic. Из них экспортируется OpenAPI, из экспорта генерируются TypeScript-типы и клиент Hey API. У операций должны быть стабильные `operationId`; генерация должна воспроизводиться и проверяться. Сгенерированные файлы вручную не редактируются. Изменение контракта сопровождается обновлением клиента и проверкой совместимости. См. [генерацию клиентов FastAPI](https://fastapi.tiangolo.com/advanced/generate-clients/) и [Hey API](https://heyapi.dev/docs/openapi/typescript/get-started).

TanStack Query управляет загрузкой и актуальностью серверных данных, а не правилами учёта. Wiki объясняет предметные правила и архитектуру; отдельная ручная копия спецификации API не ведётся. Назначение библиотеки описано в [обзоре TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview).

## Размещение кода

Схема каталогов отделяет части приложения с разными зависимостями и способами проверки.

| Путь | Назначение |
| --- | --- |
| `backend/src/takt/` | Python-пакет приложения, организованный по областям ответственности |
| `backend/tests/` | Проверки расчётов, сценариев, доступа и HTTP API |
| `backend/migrations/` | Миграции Alembic, отдельно от кода приложения |
| `frontend/src/` | Код интерфейса и интеграция с Telegram |
| `frontend/src/api/generated/` | Сгенерированный клиент; ручной код обращения к API размещается вне этого каталога |
| `frontend/tests/` | Проверки интерфейса и его взаимодействия с сервером |
| `docs/ru/`, `docs/en/` | Главная страница и проектный обзор на двух языках |

Тесты находятся рядом с соответствующей частью приложения. Назначение пути определяет, какие изменения в него попадают.

## Интерфейс

Интерфейс должен иметь собственный характер Takt, ясную иерархию времени и действий, обоснованную плотность информации и удобное исправление отметок. Композиция экранов определяется пользовательскими сценариями.

Композиция должна учитывать состояния дня: ещё не начат, идёт учёт, перерыв, норма выполнена, запись требует исправления, сервер недоступен. При отображении данных важны ограниченная ширина Telegram, экранная клавиатура, тема, доступность и повторное открытие Mini App. Визуальное оформление не определено; прежний макет с карточками не принят за референс.

## Сопровождение документации

Документация хранится рядом с кодом, чтобы изменение поведения, API или настроек и его описание проверялись в одном pull request. Отдельная GitHub Wiki имеет [собственный Git-репозиторий](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages); параллельная редактируемая копия материалов там не ведётся.

В `docs/ru/` и `docs/en/` используются одинаковые относительные пути. Имена файлов — на английском, в lowercase-kebab-case; внутренние ссылки относительные и ведут на существующие страницы выбранного языка. При изменении смысла обновляются обе версии: требования, ограничения, числа, примеры и статус решений должны совпадать. Идентификаторы и имена API не переводятся. Термины сохраняют соответствие: «интервал присутствия / attendance interval», «учтённое время / credited time».

У каждого правила одно основное место описания. Обзор объясняет систему и ссылается на подробности, не дублируя их.

Существенные архитектурные решения оформляются короткими ADR (architecture decision records): контекст, решение, последствия и статус — «Предложено», «Принято», «Отклонено» или «Заменено». Принятие решения не означает завершение реализации. Заменённая запись сохраняет контекст и ссылку на замену.

Технический текст объясняет действия компонентов, причины решений и существенные условия. Примеры содержат исходные данные, единицы и результат; утверждения о технологиях сопровождаются ссылками на их документацию. Английские заголовки оформляются в sentence case. Перед слиянием проверяются переводы, расчёты, ссылки и отображение Markdown. Инструкции запуска описывают проверенные команды.

## Проверки документации

[GitHub Actions](../../.github/workflows/documentation.yml) выполняет четыре проверки: формат Markdown, UTF-8, внутренние ссылки и соответствие русской и английской документации. Проверка переводов сопоставляет набор страниц, числа, технические идентификаторы, источники и переходы между языками. Смысловую точность перевода проверяют при чтении.

Для локального запуска инструментов проверки используется Node.js 24.13.0. Команды выполняются из корня репозитория:

```sh
npm --prefix .github/checks ci --ignore-scripts
npm --prefix .github/checks run check:markdown
npm --prefix .github/checks run check:encoding
npm --prefix .github/checks run check:links
npm --prefix .github/checks run check:translations
npm --prefix .github/checks test
```
